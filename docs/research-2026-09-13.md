# 世界大学排名重构调研

调研时间：2026-09-12 至 2026-09-13。范围：现有前端、数据流水线、PostgreSQL、两套 S3、Astro 官方文档。远端仅执行代码阅读、只读 SQL、对象列表和少量图片读取，未修改代码、数据库、存储对象或部署。本地仅新增本文档。

## 结论

推荐采用 **Astro 静态生成 + Tailwind CSS 4 + React 交互岛 + shadcn/ui + TanStack Table**。数据库查询、数据清洗、校友抽样和图片拼接放在离线数据流水线；网站构建消费已经导出的文件，网站运行只请求静态 HTML、JSON、图片及脚本。

现有组件和依赖有较高复用价值；真正需要优先解决的是数据契约和排名口径。2026 原型不能直接视为完整迁移结果：它截取前 1000 所大学、遗漏功能，并对国家和排名数据做了简化。

## 3. 数据规模与质量

以下为本轮实际读取的数量；源文件主要采用 `20251201` 快照标识，不能仅凭新网站年份将所有来源标成 2026。

| 数据 | 实测规模 |
| --- | --- |
| 2026 最终成绩 Parquet | 16,149 行，16,133 个唯一大学 ID |
| 候选大学 Parquet | 106,482 所，文件约 417 MiB，包含正文等大字段 |
| OpenAlex 链接 Parquet | 16,133 个唯一大学 ID |
| 美国 NCES 链接 Parquet | 2,843 个唯一大学 ID |
| 高考链接 / 统计 Parquet | 各 983 个唯一大学 ID |
| 校友关系 Parquet | 2,984,735 行，1,975,392 个唯一人物 ID |
| 旧综合榜数据库表 | 2,000 所；其中 1,915 所在新成绩文件中，85 所缺失 |
| `dev.university_alumnus` | 精确计数 1,884,702 行及唯一人物 ID |
| `dev.entity_images` 含 `avatar_v1` 的记录 | 553,922 条，涉及 306,321 个唯一实体 ID；未逐一确认均为校友 |

### 必须先处理的问题

1. **成绩重复来自可定位的上游连接问题。** Nature Index 链接文件有 4,498 行、4,482 个唯一 ID；其重复 ID 集合与最终成绩的重复 ID 集合完全一致。计分脚本直接按 ID 左连接该文件。最终成绩的 13 组重复大学共多出 16 行；`Q859363` 甚至有两个不同总分，不能用无规则的 `unique()` 随意保留一条。应先明确链接冲突处理规则，再重算成绩和名次。
2. **旧榜覆盖不能自动丢失。** 85 所旧榜大学未进入新成绩，需要形成缺失清单，区分身份合并、排除和数据缺失；本轮尚未逐校归因。
3. **国家应优先使用结构化字段。** 已生成的 1000 校 JSON 有 98 所标为 `UN`。其导出脚本从英文 infobox 猜国家；用 OpenAlex `country_code` 连接全部成绩时只有 6 所为空。应优先结构化字段，再用旧位置表等回退，最后标未知。
4. **名称必须有回退。** 以上全量连接有 14 条英文 label 为空、7,600 条中文 label 为空；英文可回退 wiki title，中文可回退百度匹配名或英文名，不能把缺失名称伪装成有中文覆盖。
5. **2026 成绩文件没有学科指标。** 已确认旧库有 20 个学科榜；若沿用，须明确为旧版数据，或等待对应新数据产出。
6. **2026 原型存在功能占位。** 学科状态没有进入实际过滤计算，校徽通过校名拼接猜测 `.edu` 域名。不能直接作为新网站的数据实现复用。

### 排名口径需要形成独立契约

旧站默认五维权重是声誉 25%、学术 50%、资金 10%、师资 5%、校友 10%。计算发生在服务端，读取旧综合榜最多 2000 校，先加权，再按集合最大值做 `log1p` 映射，最后按四位小数判断并列名次。国家和名称过滤发生在排名之后。

2026 流水线采用相同顶层权重，但综合分直接加权，名次使用 ordinal，完全相同的分数也分配不同序号。2026 原型默认直接使用导出成绩，修改权重后才重新线性加权，且输入分数已四舍五入到两位小数。

推荐让新数据明确携带 `officialScore`、`officialRank`、未四舍五入的五维指标、`scoringVersion`、`rankUniverse` 和并列规则。自定义权重结果单独表达；列表、详情和对比使用同一份规则。展示校友的抽样不改变全量校友统计和校友维度分数。

## 4. 静态数据组织与按需加载

建议数据发布包结构如下，路径仅为方案：

```text
public/data/<release>/
  manifest.json
  ranking/core.json
  ranking/subjects/<subject>.json
  universities/<qid>/profile.<locale>.json
  universities/<qid>/alumni.json
  universities/<qid>/nces.json
  universities/<qid>/gaokao.json
public/media/<release>/
  logos/<qid>.webp
  alumni/<qid>.<hash>.webp
```

`manifest` 描述 schema 版本、发布日期、源快照、指标版本、学校数、文件哈希和可用模块。数据与图片先完整上传，再切换对应站点版本；发布使用版本目录，防止缓存将新名单与旧雪碧图混用。

首页由 Astro 预生成默认榜首屏，交互岛加载精简榜单后开放完整搜索、过滤和调权。大学基础介绍、SEO 信息和默认分数静态生成；校友、课程、NCES 等按进入页面或展开模块再请求。排名索引按需要保留双语名，长简介按语言拆分。

**按页面切成 100 条不能独立支持全局自定义排名。** 调权必须取得全部“纳入排名范围”的五维指标，不能只对已加载页面重排。这里的全量指经过明确收录规则筛选的集合，并非默认把全部候选机构都纳入正式榜单。

实际体积测量：

- 当前 1000 校榜单：322,002 字节，gzip 后 48,409 字节。
- 当前 1000 份简化详情：合计 824,199 字节。
- 16,133 校精简榜单：包含 ID、双语 label、国家、五维原始分、总分、名次，紧凑 JSON 为 5,232,424 字节，gzip 后 1,337,142 字节，约 1.28 MiB。

最后一项在远端内存中临时合并和压缩，未落盘；为体积估算临时保留重复 ID 的第一条，并非正式去重方案。实际发布还可能增加名称回退、校徽引用、大洲等字段，体积需要重新测量。当前结果支持静态方案的可行性，但尚未做手机端排序、解压、解析或水合性能测试。

## 5. 校友照片和雪碧图

数据库通过 `educated_at` 数组关联大学，已存在 GIN 索引；图片表 `qid` 有索引。离线抽样可复用它们，避免每次页面访问触发数据库排序和图片选择。

已从图片 S3 实际读取三个对象，均为 **120×150 WebP**，大小分别为 3232、3284、3232 字节。这三个对象属于同一人物的图片变体，只证明抽查链路可用，不代表全库图片覆盖率或质量。

旧站 SQL 要求有 `avatar_v1`，实际返回的却是 `webp_resize_v1.path`，因此展示小头像时仍可能请求大图。新流水线可直接读取 `avatar_v1.path`。

推荐处理方式：

1. 按大学关联人物，人物 ID 去重并验证关系质量；只从有可用头像和名称的候选中选择。
2. 每校数量做成参数，建议默认 16 人。使用固定种子抽样，可结合影响力排序设候选池；具体抽样规则记录在发布元数据中，保证同版结果稳定。
3. 按人物 ID 缓存下载结果；跨校同一人物只下载一次。缺失对象或解码失败进入报告并回退占位。
4. 每校生成一张小型 WebP 图集和坐标清单。16 人按 4×4 排列、每格 120×150 时为 480×600，另按需要增加边距。图集按校请求，避免全站巨图。
5. 页面用固定宽高与背景坐标展示，保留可访问的姓名文本；接近校友区域时才设置图集地址，CSS 背景本身不能靠 `loading="lazy"` 延迟加载。

已有 Python 流水线依赖 boto3、Pillow 和人脸裁剪工具，优先复用现成裁剪图并用 Pillow 拼接即可。如导出阶段选择 TypeScript，则可采用 AWS S3 SDK + Sharp `composite`。本轮未生成实际雪碧图，最终图集体积和视觉效果仍需样本验证。

## 6. 推荐技术选型

| 用途 | 建议 | 原因 |
| --- | --- | --- |
| 页面框架 | Astro，显式静态输出 | 预生成双语页面与详情，运行时不依赖应用服务器 |
| 交互 | `@astrojs/react`、React | 复用现有排名控件和复杂详情组件；主排名岛及时加载，较重模块延迟加载 |
| 样式 | Tailwind CSS 4、`@tailwindcss/vite` | 使用官方推荐的 Tailwind 4 接入方式 |
| UI 组件 | shadcn/ui、Radix、Lucide | 旧项目已有大量相同组件；shadcn 官方支持 Astro |
| 表格 | TanStack Table | 复用排序、筛选、分页能力；分页已足够时不额外引入虚拟滚动 |
| 请求缓存 | 原生 fetch 起步；多模块共享请求时复用 TanStack Query | 查询静态 JSON，不再保留 tRPC 协议和服务器层 |
| 图表 | 复用 Recharts，模块延迟加载 | 已有 React 生态，避免另建图表实现 |
| 数据校验 | Zod / Astro 内容集合 schema；Python 侧复用现有校验能力 | 明确缺失字段、版本和 ID 唯一性 |
| 离线数据 | Polars、psycopg、boto3、Pillow | 流水线已安装，直接覆盖读取、抽样和图片产出 |
| 部署 | 静态 HTTP 服务，HTML/JSON/媒体版本化与 gzip/Brotli | 部署产物只有静态文件，无 DB/S3 凭据，无常驻 Next.js 进程需求 |

“尽可能多用轮子”在这里适合表现为复用现有成熟组件和数据工具；无需为 1.6 万条结构化数据先加入浏览器数据库或全文检索引擎。需要模糊搜索时再选择对应工具。

Astro 官方文档确认可在构建时生成动态路径对应的静态页面/JSON；`public` 文件可直接作为静态资源发布。业务数据既可用文件加载器组织，也可由外部流水线预生成，不需要为读取本地 JSON 建一个后端。

## 7. 建议实施顺序与验收

1. **数据契约与质量修复**：解决 Nature Index 重复连接、梳理 85 校覆盖差异，明确正式收录集合、评分和学科版本；导出质量报告。
2. **打通少量真实样本**：选中、美及其他地区大学，生成基础 JSON、校徽、固定校友样本和雪碧图，验证来源字段、空值与异常图片。
3. **Astro 主流程**：双语静态首页、排名搜索筛选、五维调权、详情与对比；迁移可复用 UI。
4. **补齐详情模块**：课程、高考、NCES、社交、坐标/地图；本期不加入新闻和校园照片。
5. **静态发布验证**：断开 DB/S3 后仍能构建已导出数据并浏览站点；检查深层路由、缓存版本、失败回退、移动端性能和交互可访问性。

与排名相关的必要验证包括：同一数据与权重在流水线和前端结果一致；重复 ID 不得进入发布包；零权重、缺失指标、并列分、过滤后名次不漂移；列表与详情/对比一致。图片验证包括坐标正确、名单顺序一致和加载失败回退。

实施前仍需明确的产品口径是：正式榜单展示/收录范围，2026 新计分与旧规则如何衔接，旧学科榜是否作为历史版保留。其他如默认每校 16 人、每校一图、双语回退可作为可配置默认值先落地。
